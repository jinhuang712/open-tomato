# ask_user 提问形态

设计交接稿。讨论结论定了，还没动代码；实现按末尾的分步来。

## 一、一句话

作者面对一个问题时要做的决策动作只有五种：开放回答、挑一个、挑若干个、逐条表态、并排对比。`ask_user` 仍是一个入口，用 `kind` 显式声明形态；界面、答案格式、逃生口都按 kind 定。

## 二、原则

**没有选也是一种选。** 作者没点某一条，是在说「这条我不表态，你看着办」。界面不阻止提交，不逼作者补齐，但回给主编的答案必须把「没表态」和「不要」分开说，因为主编对这两种要做的事不一样：不要就丢掉，没表态是主编自己拿主意并且在 say 里说一句。「先放一放」「你替我定」这些逃生口都是这条原则的不同形态。

**入口一个，形态显式，推断当兜底。** 不拆成五个工具：内核到处认的是 `toolName === "ask_user"`（`asked` 标记、pause-lead 只准最后问一次、AskCard、测试），拆开等于改最核心的一条循环。选错 kind 时候选还在，`repairAskArgs` 能按形状纠正；选错工具则 schema 直接对不上，校验打回，作者面前是一条红色报错。`kind` 缺失或与 options 形状不符时按形状定，最坏退回到今天的行为。

**say 与 question 的分工不变。** 铺垫、候选各自的路子和代价放 say，question 一两句只装问题。这一点五种形态一样。

## 三、五种形态

| kind | 作者的动作 | options 形状 | 现状 |
|---|---|---|---|
| `open` | 自由回答 | 空 | 有。但工具描述写着「每次都要给 options」，等于在提示词层把它否了，要改 |
| `single` | 挑一个，点即发 | 短字串 2–6 个 | 有 |
| `multi` | 挑若干个，再点确定 | 短字串 2–8 个 | 缺 |
| `checklist` | 每条独立表态：改 / 不改 / 没碰 | 条目 2–8 个 | 缺 |
| `compare` | 并排读长稿，选一版 | `{label, text}` 2–4 个 | 有，但靠「超过 40 字或含换行」推断，书名候选一长就会被误判成对比稿 |

`multi` 和 `checklist` 的边界：multi 的没选是干净的「不要」，一句「选了 A、C」就够；checklist 的没选是「留给你」，必须单独报。审稿回来一堆意见问「返修哪几条」是 checklist，不是 multi；评审派哪几个角色是 multi。

## 四、数据模型

```ts
type QuestionKind = "open" | "single" | "multi" | "checklist" | "compare";

type QuestionOption =
  | string                          // single / multi / checklist 的短候选
  | { label: string; text: string }; // compare 的长稿

interface QuestionRequest {
  questionId: string;
  agentId: string;
  text: string;
  kind: QuestionKind;               // 内核补齐，渲染层不做推断
  options: QuestionOption[];
  allowFreeText: boolean;
}
```

`ask_user` 参数加 `kind?: QuestionKind`。`repairAskArgs` 负责补齐与纠正，规则按优先级：

1. options 为空 → `open`
2. 任一候选是 `{label, text}` → `compare`
3. 任一纯字串含换行或超过 40 字 → `compare`（兼容旧行为，模型给了 `single` 也覆盖掉）
4. 模型给了合法 kind → 用它
5. 否则 → `single`

`kind` 加进 `ASK_ARG_KEYS`，漏进 options 的键名照旧摘掉。

## 五、回给模型的答案格式

仍是一个字符串，gate 和 runtime 不改。格式要让主编不用猜：

| kind | 答案 |
|---|---|
| open | `作者回答：<原文>` |
| single | `作者回答：<label 或全文>` |
| multi | `作者选了：A、C` |
| checklist | `作者逐条表态。改：第 1、3 条；不改：第 2 条；没表态：第 4、5 条` |
| compare | `作者选了：<label>` |
| 逃生口 / 自由输入 | `作者回答：<逃生口预设的指令或原文>` |

checklist 的三组一组都不省，空组写「无」。条目引用用序号加短名，比如「第 1 条（开头太慢）」，方便主编在 say 里转述。

## 六、界面

组件仍是 QuestionDock 一张卡，头部、折叠、自由输入框不变。中段按 kind 分五种：

**open**：没有 chip，只有输入框和逃生口。

**single**：现状。chip 一行铺开，点即发。

**multi**：chip 可切换勾选态（描边变实、带勾），底部多一个主按钮「确定（已选 N 项）」。N 为 0 时按钮禁用，想表达「都不要」走逃生口或自由输入。

**checklist**：每条一行，左侧条目正文，右侧两个小按钮「改」「不改」，三态互斥可取消。底部主按钮「确定」随时可点，未表态的条目不标红不提示。已表态的行略微变淡，让作者看得出哪些还没碰。

**compare**：现状的稿纸并排。`{label, text}` 里 label 做稿纸标签，text 渲染 Markdown。

自由输入框的 placeholder 按 kind 换：open 是「输入回答…」，single/multi 是「或者直接输入…」，checklist 是「有别的要改的，直接说…」，compare 是「都不满意？说说想怎么改，或者把两版混搭…」。

## 七、逃生口

永远由界面补，不靠模型给。按 kind 定：

| kind | 逃生口 |
|---|---|
| open | 我还没想好（让主编先给 3 个候选）· 先放一放 |
| single | 换一批 · 你替我定 · 先放一放 |
| multi | 换一批 · 你替我定 · 先放一放 |
| checklist | 全改 · 全不改 · 没碰的你替我定 · 先放一放 |
| compare | 混搭 · 都不太对 · 先放一放 |

checklist 的「没碰的你替我定」是半自定半委托：作者点几条再点它，等于把已表态的交出去、没表态的委托出去。它提交的答案是三组表态加一句「没表态的你替我定，说清为什么」。

## 九、分步实现

每步独立可提交、可跑。

1. **协议与工具参数**：`protocol.ts` 加 `QuestionKind` 和 `kind` 字段；`ask-user.ts` 加参数；`repairAskArgs` 按第四节规则补齐。渲染层暂时忽略 kind，`hasLongOptions` 还在，行为不变。加 `repairAskArgs` 的测试。
2. **渲染层改用 kind**：QuestionDock 用 `request.kind` 分支，`hasLongOptions` 只留给 AskCard 或删掉。行为仍不变。
3. **multi**：chip 勾选态、确定按钮、答案格式、逃生口。
4. **checklist**：三态行、确定按钮、三组答案格式、逃生口。
5. **提示词与文档**：第八节四处。

第 1、2 步是纯重构，第 3、4 步各是一个功能，第 5 步最后做，因为要等界面真能接住再教主编用。

## 十、待定

- checklist 条目要不要允许 `{label, text}`（一条意见带完整原文）。倾向先不支持，意见原文在 say 里转述，条目只放一句话。
- multi 要不要给上限。倾向 8 个，超过就该是 checklist 或分两问。
