# 设计思想

open-tomato 是作者与一组 AI 角色共同写长篇的工作台。这里记的是我们做取舍时依据的原则，不是功能清单。原则应该少而稳，改它要比改代码慎重。

## 一、作者是唯一的决策者

AI 角色再多，方向性的决定只有作者能做：故事讲什么、人物叫什么、卷怎么切、设定推不推翻。角色的职责是把选择摆清楚，不是替作者选。

由此推出：

- 开放问题也要给出具体候选，作者点一下就能往下走，而不是面对空白框。
- 摆清楚选择包括摆清楚代价。作者要的方向与已有材料冲突，或在工艺上有明显代价，在候选上说一次；作者选定之后依他，同一件事不再提。
- 一次只问一件事。多个决定串着问，别把三个问题塞进一个选项列表。
- 留白是合法的，留白的形态是「不出现」。没聊到的段不落盘，写到了再新增一段；不为了完整硬填，也不写「待定」占位——占位对读的人是噪音，对模型是催填的信号。
- 作者明确说「先放一放」的项是一个悬而未决的决定，不是内容。它记在卡的 frontmatter `open` 清单里，拍板后去掉；机检和侧栏读它来提醒，正文段落里不出现。

## 二、讨论在落盘之前

作者要看的是方向对不对，不是成品对不对。一张卡从无到有应该经过：出候选 → 作者挑一个或混搭 → 在选中的候选上孵化 → 落盘确认。

审批门守的是最后一步。如果作者第一次看到内容就是在审批门上，流程已经错了。

## 三、代码管「能不能」，提示词管「该不该」

协作完全靠提示词不行，完全靠代码更不行。

- **违反了会让体验直接坏掉的，用代码堵。** 手段是剥工具、保留会话、schema 限制，而不是在提示词里多加一句「请不要」。
- **需要看情境权衡的，留给模型。** 候选给几个、差异怎么拉开、什么时候续接什么时候重派，写死就僵了。
- **模式由角色按情境选，代码不强制顺序。** 作者已经拍板时，不必被流程逼着再走一遍候选。

判断一条约束该放哪一边，问一句：违反它的代价是「不好」还是「坏掉」。前者交给提示词，后者交给代码。

同一条约束只写一处。能力脚本和角色提示里各写一遍，模型收到的信号就从「建议」变成「流程」，情境判断的空间随之消失。访谈曾把问题顺序在两处各写死一遍，结果是一份固定问卷。

结果确定、只读、便宜的机械活，也不该等人来点。机检就是这样：文档一变内核就自己跑一遍，侧栏的红黄点始终是最新的；模型每次落盘的返回里附带这篇的机检结果，写完当场知道漏了什么。作者和模型都没有「记得去检查」这项负担，界面上也不留按钮。

## 四、角色各守边界，主编负责统筹

主编不写正文、不设计人物，只判断阶段、派任务、汇总候选、把决定交给作者。创作角色只在自己的类别里动手。评审角色只读不写。

边界靠能力集实现：一个角色拿不到的工具，就是它不该做的事。这样边界不依赖模型自觉。

子 agent 面向主编交付，不面向作者说话。它没有向作者提问的通道，作者的决定经主编转达。

## 五、上下文是资产，不重写

一个角色出完候选后，作者拍板、它接着孵化，应当是同一个会话在延续。重派一个新角色从头再写，丢的是它对候选之间取舍的理解，也让作者的拍板失去对象。

由此推出：子 agent 完成一轮不等于退场，会话保留到主编决定不再需要它。

## 六、创作不停车，但停在正确的点

阶段一收口就该推下一步，不把「你有空再说」留给作者。但推的方式是给出下一步的候选让作者选，而不是替作者往前跑。

「不停车」与「先讨论」不矛盾：停在候选上等拍板，是流程里正确的停顿；停在阶段之间等作者想起来，才是需要消除的停车。

不停车的形态是一个循环，而不是一条流水线。主编做完一件就取下一件：作者的话和批注排最前，作者拍板了的其次，然后是机检必须修的，再是这本书欠的账，最后才是下一章。写之前要看素材够不够，素材不够要问，作者有新想法要接着聊，这些都是活。这本书写完之前活不会没有，所以循环不会停；但每一件都停在门后等作者，主编可以往前备，不能往前定。

## 七、材料结构是协作的公共语言

所有材料都是带 frontmatter 的 Markdown，按类型分目录，每类有一份字段与段落的 schema：哪些必填、哪些可选、哪些在什么条件下转为必填（主角的语音签名必填，配角的可选）。模板由 schema 渲染，只出现必填的部分；可选部分写到了才出现。这不只是存储格式，是角色之间、角色与作者之间的共同约定：一张卡该有什么，读它的人不用猜；机检报的是「缺必填段」「残留待填」而不是主观判断。

schema 写在代码里，是这份约定的唯一来源：模板、机检、给模型看的可选段清单都从它推导，不在提示词里再抄一份。必选与可选的划分会随实际协作调整，调整只改 schema 一处。

写正文只需要章纲、前一章结尾、在场人物的语音签名和守则。材料结构的目标就是让每个角色只读它该读的，而不是通读全库。

材料分两种形态。描述「故事里有什么」的是卡：世界设定、人物、线索，一张卡一个对象，路径就是名字。约束「怎么写」的是守则：一条一卡，只追加不删改，标题就是规则本身，用 level（必须 / 尽量）和 scope（管哪一块）区分，而不是按强度或范围拆成几份文件。这本书是什么则是一份「简介」，全书只有一份，路径即名字。

一份材料对外只有一个名字。侧栏、审批卡片、模型的话里出现的必须是同一个词：路径即名字的直接显示路径，编号存储的一律显示标题。同一份东西在两个地方叫两个名字，作者就得在脑子里维护一张映射表。

---

这些原则大多来自实际协作中踩过的坑。新增一条原则时，先确认它不是某次具体事故的应急处理，而是会反复出现的取舍。
