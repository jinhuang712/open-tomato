# 设计思想

open-tomato 是作者与一组 AI 角色共同写长篇的工作台。这里记的是我们做取舍时依据的原则，不是功能清单。原则应该少而稳，改它要比改代码慎重。

## 一、作者是唯一的决策者

AI 角色再多，方向性的决定只有作者能做：故事讲什么、人物叫什么、卷怎么切、设定推不推翻。角色的职责是把选择摆清楚，不是替作者选。

由此推出：

- 开放问题也要给出具体候选，作者点一下就能往下走，而不是面对空白框。
- 摆清楚选择包括摆清楚代价。作者要的方向与已有材料冲突，或在工艺上有明显代价，在候选上说一次；作者选定之后依他，同一件事不再提。
- 一次只问一件事。多个决定串着问，别把三个问题塞进一个选项列表。
- 留白是合法的，留白的形态是「不出现」。没聊到的段不落盘，写到了再新增一段；不为了完整硬填，也不写「待定」占位——占位对读的人是噪音，对模型是催填的信号。
- 作者明确说「先放一放」的项是一个悬而未决的决定，不是内容。它记在卡的 frontmatter `open` 清单里，拍板后去掉；机检和侧栏读它来提醒，正文段落里不出现。

## 二、讨论在落盘之前

作者要看的是方向对不对，不是成品对不对。一张卡从无到有应该经过：出候选 → 作者挑一个或混搭 → 在选中的候选上孵化 → 落盘确认。

审批门守的是最后一步。如果作者第一次看到内容就是在审批门上，流程已经错了。

审批门放过什么，按字段的含义分，不按它在文件里的位置分。正文没变不等于故事没变：人物从主角改成配角、章纲换了所属卷、多挂了一条线索，正文一字未动，作品结构已经变了，这些照样过门。放行的只有记账字段（状态、关键词、待办清单、字数计数），改了哪些写在回话里让作者看见。

## 三、代码管「能不能」，提示词管「该不该」

协作完全靠提示词不行，完全靠代码更不行。

- **违反了会让体验直接坏掉的，用代码堵。** 手段是剥工具、保留会话、schema 限制，而不是在提示词里多加一句「请不要」。
- **需要看情境权衡的，留给模型。** 候选给几个、差异怎么拉开、什么时候续接什么时候重派，写死就僵了。
- **模式由角色按情境选，代码不强制顺序。** 作者已经拍板时，不必被流程逼着再走一遍候选。

判断一条约束该放哪一边，问一句：违反它的代价是「不好」还是「坏掉」。前者交给提示词，后者交给代码。

同一条约束只写一处。能力正文和角色提示里各写一遍，模型收到的信号就从「建议」变成「流程」，情境判断的空间随之消失。访谈曾把问题顺序在两处各写死一遍，结果是一份固定问卷。

结果确定、只读、便宜的机械活，也不该等人来点。机检就是这样：文档一变内核就自己跑一遍，侧栏的红黄点始终是最新的；模型每次落盘的返回里附带这篇的机检结果，写完当场知道漏了什么。作者和模型都没有「记得去检查」这项负担，界面上也不留按钮。

## 四、角色各守边界，主编负责统筹

主编不写正文、不设计人物，只判断阶段、派任务、汇总候选、把决定交给作者。创作角色只在自己的类别里动手。评审角色只读不写。

边界靠能力集实现：一个角色拿不到的工具，就是它不该做的事。这样边界不依赖模型自觉。

「只在自己的类别里动手」也是能力集的一部分，不只是提示词里的一句话。每个角色声明能写哪几类材料：写手只有正文，策划只有三类卡，编剧是三层大纲加线索卡的回写，主编是简介、守则和拍板后的骨架卡。写工具的参数只列这几类，落盘前再查一次；越界的调用不进审批门，直接打回，让它把要改的内容写进报告交主编派人。

子 agent 面向主编交付，不面向作者说话。它没有向作者提问的通道，作者的决定经主编转达。

这条边界按派单方式分两段。候选轮（propose）方向没定，作者的意见要经主编汇总成一问再拍板，所以作者不直接和子 agent 说话，界面上它的输入框是关着的。落盘轮（commit）作者已经拍板，子 agent 孵化的是具体的东西，审批放行、退回理由、圈一段说改法，都是它自己接得住的活，作者直接对它说；主编只收最后的报告。

主编对作者说话是显式动作：普通表达走 `say`，需要作者回答时走 `ask_user`。共同的沟通原则放在主编提示词，两个通道的用途和表达要求放在各自工具描述，不重复维护。

解释可以直接放在 `ask_user.say`，无需先独立调用 `say`；前文已经讲清时可以省略。报告的转述关注当前决定所需的信息，不要求逐项复述。内核只阻止尚有未解释报告且提问完全没有解释的情况，两个通道的非空表达都算转述，空白不算。

沟通允许讨论、探索、判断和自然结束，不要求每次产生任务。主编保留独立判断与创造性，区分探索、决定和执行授权；正式材料的权限与审批不变。

没有选也是一种选。作者没点某一条，是在说「这条我不表态，你看着办」。界面不阻止提交、不逼作者补齐，但回给主编的答案必须把「没表态」和「不要」分开说，因为主编对这两种要做的事不一样：不要就丢掉，没表态是主编自己拿主意并且在 say 里说一句。多选的没选是干净的「不要」，一句「选了 A、C」就够；逐条表态的没选是「留给你」，必须单独报。「先放一放」「你替我定」这些逃生口都是这条原则的不同形态。

## 五、上下文是资产，不重写

一个角色出完候选后，作者拍板、它接着孵化，应当是同一个会话在延续。重派一个新角色从头再写，丢的是它对候选之间取舍的理解，也让作者的拍板失去对象。

由此推出：子 agent 完成一轮不等于退场，会话保留到主编决定不再需要它。

「不再需要」是判断，不是计时：候选悬着等作者拍板的可能隔一夜才续，按时间自动清理会删掉正要续的那位。所以退场是主编的一个显式工具，作者在名单里也能亲手让某位退场，内核不做自动回收。

但保留不等于都摆在眼前。界面上的在场名单只放需要作者注意的人：在跑的、出错的、正看着的。歇着的折成一个数字，点开才列出来。名单管「现在谁需要你」，派单卡管「谁干过什么」，历史归档不由名单承担。

## 六、按作者意图推进，允许自然结束

作者正在推进创作时，主编优先处理作者的话和批注，再处理已拍板的工作、必须修的问题与长期搁置项。需要作者取舍时讲清再问，不能替作者越过决定和审批。

讨论、解释和探索本身也有价值。问题已经回答清楚时可以结束，不要求每轮都安排下一件事；后台工作和新的作者消息仍继续接入。

内核只在主编没有可见回应、没有提问、没有后台任务且收件箱为空时补一次回应提示。已经发送非空对话即可自然结束，不强制提问或推进下一件事；新消息与后台报告仍照常唤起主编。

派单不阻塞主编。子 agent 在后台跑，报告做完了作为一条新消息进主编的收件箱，和作者的话排在同一条队里。主编「等」的形态是不往前定：候选没回来，不开同一件事的新派单、不替作者选方向；但作者这时说的话照常接、照常答。曾经派单是一个阻塞的工具调用，策划出候选的几分钟里主编卡着，作者说话只能排队——那不是设计里的停顿，是机制的副作用。

## 七、材料结构是协作的公共语言

所有材料都是带 frontmatter 的 Markdown，按类型分目录，每类有一份字段与段落的 schema：哪些必填、哪些可选、哪些在什么条件下转为必填（主角的语音签名必填，配角的可选）。模板由 schema 渲染，只出现必填的部分；可选部分写到了才出现。这不只是存储格式，是角色之间、角色与作者之间的共同约定：一张卡该有什么，读它的人不用猜；机检报的是「缺必填段」「残留待填」而不是主观判断。

schema 写在代码里，是这份约定的唯一来源：模板、机检、给模型看的可选段清单都从它推导，不在提示词里再抄一份。必选与可选的划分会随实际协作调整，调整只改 schema 一处。

写正文只需要章纲、前一章结尾、在场人物的语音签名和守则。材料结构的目标就是让每个角色只读它该读的，而不是通读全库。

材料分两种形态。描述「故事里有什么」的是卡：世界设定、人物、线索，一张卡一个对象，路径就是名字。约束「怎么写」的是守则：一条一卡，只追加不删改，标题是规则的短句、摘要是规则完整的一句话、正文写边界与例外，用 level（必须 / 尽量）和 scope（管哪一块）区分，而不是按强度或范围拆成几份文件。这本书是什么则是一份「简介」，全书只有一份，路径即名字。

一份材料对外只有一个名字。侧栏、审批卡片、模型的话里出现的必须是同一个词：路径即名字的直接显示路径，编号存储的一律显示标题。同一份东西在两个地方叫两个名字，作者就得在脑子里维护一张映射表。

## 八、能力是主编的打包工作流，不是界面的功能入口

立项访谈、聊一张卡、大纲编排、多路审稿、卷末盘点，这些是主编手里打包好的几段工作流，叫能力。一条能力写的是这段工作的目标、交付物长什么样、什么算做完、哪些坑别踩；不写步骤。怎么走由主编看盘面定：同一条「聊一张卡」，白纸时和写到第八章时开口完全不同。写成第一步第二步，模型就照本宣科，进场第一句话与作者刚说的话对不上。

能力在主编的循环里，不在界面上。清单进主编的系统提示，进场是一次工具调用。三种进场共用同一份清单和同一份正文：作者点了界面上的按钮；主编看盘面觉得该做了，自己进；主编觉得该做但拿不准作者此刻要不要，先问一句，作者应了再进。按钮只是作者替主编发起的那一次调用，不是另一条通路。

能力不收参数。哪一章、哪张卡、哪一卷，盘面上都有，主编自己读；读不到再问作者。曾经按钮点下去先弹一张表单让作者填章号，等于在主编开口之前塞了一道表，作者要先替主编把盘面看一遍。

界面上的按钮是作者说话的快捷方式，数量少而稳，按阶段只露当下该做的几个。作者面对的始终是一个对话，不是一排功能。

---

这些原则大多来自实际协作中踩过的坑。新增一条原则时，先确认它不是某次具体事故的应急处理，而是会反复出现的取舍。
